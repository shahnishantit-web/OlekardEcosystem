# Financial Integrity Checklist: Platform Foundation

**Purpose**: Independently validate that Platform Foundation's financial-integrity requirements are sufficiently precise, complete, and consistent for implementation. This checklist is a requirements-quality audit — not an implementation test.
**Created**: 2026-08-16
**Feature**: [Platform Foundation Specification](../spec.md) · [Implementation Plan](../plan.md) · [Contracts](../contracts/) · [Data Model](../data-model.md)

**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and confirmed as adequately specified. It does NOT mean implementation work is complete.
**Classifications** (author-supplied, reviewer must confirm): **PASS** = well-specified; **GAP** = missing or insufficiently precise detail; **BLOCKING** = prevents safe financial implementation without resolution; **TBD/DEFERRED** = intentionally open per constitution or scope boundary.

## 1. Money Representation

- [x] CHK001 — Is the canonical in-memory money representation (integer, smallest currency unit — e.g., thebe for BWP) reconciled with the database storage format (`NUMERIC(19,4)`) and is the conversion point (application layer? DB layer? never?) specified? [Consistency, Spec §FR-024, contracts/module-contracts.md §MoneyContract] — **GAP → RESOLVED** — FR-181 added: in-memory is `int` (smallest unit); DB is `NUMERIC(19,4)`; conversion occurs exclusively at the Infrastructure layer; domain/application layers operate on integers only
- [x] CHK002 — Is the prohibition on FLOAT/DOUBLE for all monetary storage — both at the database column level and in any in-memory intermediate calculation — stated explicitly as a hard requirement? [Completeness, Spec §FR-024] — **PASS** — FR-024 states "never FLOAT" for decimal/money values
- [x] CHK003 — Are currency-specific precision rules (number of decimal places per ISO 4217 currency code — e.g., BWP = 2, JPY = 0, BHD = 3) specified as a required lookup, or is this left to domain-epic convention? [Completeness, contracts/module-contracts.md §CurrencyContract] — **GAP** — `CurrencyContract.precision()` exists but the authoritative source for per-currency precision values is not specified (ISO 4217 is implied but not stated as the reference); two implementers could choose different sources
- [x] CHK004 — Is cross-currency arithmetic (adding or subtracting `MoneyContract` values of different currencies) explicitly prohibited at the contract level, or must the caller check before calling? [Completeness, contracts/module-contracts.md §MoneyContract] — **GAP** — `MoneyContract.add()` and `subtract()` accept any `MoneyContract` argument; no requirement states whether the contract must throw on currency mismatch or whether the caller is responsible for the guard
- [x] CHK005 — Are negative monetary amounts explicitly permitted or prohibited, and if permitted, are the valid use cases (refunds, reversals) specified? [Completeness, Gap] — **GAP** — `MoneyContract.isPositive()` implies negative amounts can exist at the object level; no requirement states whether a negative-amount MoneyContract is valid, invalid by construction, or valid only in specific reversal contexts
- [x] CHK006 — Is the idempotency key format (UUID v7 specifically, not any UUID) consistent between the spec requirement (FR-043: "UUID v7 or equivalent time-ordered") and the data model (idempotency_keys table: `varchar(255)` without UUID type constraint)? [Consistency, Spec §FR-043, data-model.md §idempotency_keys] — **GAP** — FR-043 accepts "equivalent time-ordered" identifiers, which permits ULID or other formats; the data model stores as varchar without format validation; whether the uniqueness constraint enforces UUID v7 format is unspecified

## 2. Idempotency Requirements

- [x] CHK007 — Is there a CONFLICT between the idempotency key uniqueness scope in data-model.md (`UNIQUE INDEX ON (idempotency_key)` — globally unique) and the scope stated in contracts/idempotency-protocol.md ("scoped to `actor_id, idempotency_key`" — per-actor unique)? [Conflict, data-model.md §idempotency_keys, contracts/idempotency-protocol.md] — **BLOCKING → RESOLVED** — data-model.md corrected: `actor_id` changed to NOT NULL (zero UUID for system calls); UNIQUE INDEX changed to `UNIQUE INDEX ON (actor_id, idempotency_key)`; FR-046 updated with composite uniqueness scope statement
- [x] CHK008 — Is the request fingerprint algorithm (SHA-256 of HTTP method + path + body) specified as a spec-level requirement, or is it only documented in the data model and contracts? [Completeness, data-model.md §idempotency_keys, Spec §FR-043–FR-046] — **GAP** — SHA-256 with `(method + "|" + path + "|" + body)` appears in data-model.md and idempotency-protocol.md but is not an explicit FR; implementers reading only spec.md could choose a different algorithm
- [x] CHK009 — Are all five idempotency conflict scenarios (completed replay, in-progress lock, payload mismatch, key expired, key missing on financial endpoint) specified with their HTTP status codes and error codes? [Completeness, contracts/idempotency-protocol.md §Conflict Behaviors] — **PASS** — contracts/idempotency-protocol.md documents all five scenarios with HTTP status and error code
- [x] CHK010 — Is behavior specified for an idempotency key reused with a different HTTP method than the original request (e.g., the original was `POST`, the replay is `PATCH` with the same key)? [Completeness, Gap] — **GAP** — the conflict table addresses payload mismatch but not method mismatch; the `http_method` column exists in the data model but no requirement specifies whether method mismatch triggers `IDEMPOTENCY_KEY_MISMATCH` or is ignored
- [x] CHK011 — Is Redis-failure graceful degradation specified — specifically that a Redis cache miss or Redis unavailability MUST fall through to PostgreSQL and MUST NOT return an error to the caller? [Completeness, Spec §FR-046, Gap] — **GAP** — FR-046 says Redis MAY be used as a cache and PostgreSQL is authoritative, but no requirement mandates that Redis failure is transparent; an implementer could let Redis connection errors propagate as 503
- [x] CHK012 — Is the boundary of "state-changing financial operations" (which endpoints require an Idempotency-Key header per FR-033) defined explicitly or by a discoverable convention? [Clarity, Spec §FR-033] — **GAP** — FR-033 says "state-changing financial operations MUST accept an Idempotency-Key header" but does not define what qualifies as a "financial operation"; domain-epic authors need a clear criterion (e.g., any operation that creates/modifies wallet/ledger/transfer records)
- [x] CHK013 — Is service-to-service idempotency key scoping (using `service_id` as the actor scope instead of `user_id`) specified as an explicit spec requirement or only in the contract document? [Completeness, contracts/idempotency-protocol.md, Gap] — **GAP** — service-to-service scoping is documented in idempotency-protocol.md but is not an FR; domain epics implementing machine-to-machine calls have no spec-level requirement to follow
- [x] CHK014 — Are idempotency records in `processing` state that persist after a worker crash (stuck-processing records) addressed by a cleanup requirement? [Completeness, Gap] — **GAP** — the TTL cleanup job (`IdempotencyCleanupJob`) removes expired records, but a record in `processing` state that has not expired (worker crashed before completing) would remain stuck indefinitely; no cleanup/timeout requirement exists for this state

## 3. Transaction Integrity

- [ ] CHK015 — Is the PostgreSQL transaction isolation level for financial write operations (INSERT/UPDATE to domain tables + outbox in a single transaction) specified as a requirement? [Completeness, Gap] — **GAP** — no FR specifies the required isolation level (READ COMMITTED vs. REPEATABLE READ vs. SERIALIZABLE) for financial operations; different isolation levels produce different concurrency semantics for wallet balance reads
- [x] CHK016 — Is the requirement that domain state change and Outbox INSERT must occur within the same PostgreSQL database transaction stated as an explicit spec requirement (not only implied by plan/contracts)? [Completeness, Spec §FR-049, FR-050, Gap] — **GAP → RESOLVED** — FR-050 updated: "The Outbox INSERT and the domain state change MUST occur within the same PostgreSQL database transaction; if either write fails, both MUST be rolled back, leaving no partial financial effect"
- [x] CHK017 — Is rollback behavior explicitly required for failed financial mutations — specifically that no partial financial effect may persist after any error? [Completeness, Gap] — **GAP** — no FR states that failed financial operations must leave zero net effect on persistent state; atomicity is implied by FR-049/050 and the outbox pattern but is not stated as a hard requirement
- [ ] CHK018 — Are deadlock detection and client-facing behavior (HTTP status code, retry guidance) specified for financial write operations? [Completeness, Gap] — **GAP** — idempotency serialization uses SKIP LOCKED (no blocking), but non-idempotency financial writes (e.g., wallet status updates) have no specified deadlock handling; no FR addresses deadlock timeout, retry, or error code
- [ ] CHK019 — Is the required locking strategy for financial balance reads-before-writes (optimistic via version column vs. pessimistic via `SELECT ... FOR UPDATE`) specified at the platform level, or is it intentionally left to the domain epic? [Completeness, Gap] — **TBD/DEFERRED** — wallet balance management belongs to E06; Platform Foundation establishes idempotency locking only; the locking strategy for balance operations is a domain-level decision
- [x] CHK020 — Is the 409 HTTP status code (FR-031) used consistently for all financial conflict types (idempotency in-progress, idempotency mismatch, business-rule conflict), and are they distinguished by error code rather than HTTP status? [Consistency, Spec §FR-031, FR-040, FR-047] — **GAP** — FR-031 specifies 409 for "conflict"; FR-040 says "400 or 409" for business-rule violations; FR-047 specifies 409 for `IDEMPOTENCY_IN_PROGRESS`; the 400 vs. 409 boundary for business-rule conflicts is ambiguous

## 4. Double-Entry Ledger Contracts

- [x] CHK021 — Is a `LedgerModuleContract` stub interface defined in Platform Foundation (as `IdentityModuleContract` is defined) so that domain epics needing to post ledger entries have a stable interface to depend on? [Completeness, contracts/module-contracts.md §Module Stub Contracts, Gap] — **GAP → RESOLVED** — `LedgerModuleContract` stub added to contracts/module-contracts.md with `postEntry()` and `entryExists()` methods; FR-185 added as spec requirement
- [x] CHK022 — Is a `WalletModuleContract` stub interface defined in Platform Foundation so that domain epics checking wallet existence, status, or ownership have a stable interface? [Completeness, contracts/module-contracts.md §Module Stub Contracts, Gap] — **GAP → RESOLVED** — `WalletModuleContract` stub added to contracts/module-contracts.md with `isActive()`, `ownerActorId()`, and `currency()` methods; FR-185 added as spec requirement
- [ ] CHK023 — Is the write-once immutability requirement (FR-082) stated specifically for financial ledger entries, or does it apply only to audit events? [Clarity, Spec §FR-082] — **GAP** — FR-082 states "Audit storage MUST be write-once"; it does not explicitly extend this requirement to ledger/journal entries; the constitution prohibits altering historical ledger entries but this is not reflected in a spec FR
- [ ] CHK024 — Is the compensating reversal requirement (new entries that offset originals, never edits to existing entries) defined at the Platform Foundation contract level or deferred to the Ledger domain epic? [Completeness, Gap] — **TBD/DEFERRED** — reversal mechanics are Ledger-domain business logic (E07); Platform Foundation establishes write-once via FR-082; the compensating reversal pattern is a domain concern
- [ ] CHK025 — Is the debit-equals-credit invariant (double-entry accounting) a platform-level contract constraint or a business rule belonging to the Ledger epic? [Completeness, Gap] — **TBD/DEFERRED** — the constitution mandates double-entry journals; Platform Foundation establishes the MoneyContract and platform audit; invariant enforcement belongs to E07 (Ledger epic)
- [x] CHK026 — Is the `platform.audit_events` write-once enforcement mechanism (REVOKE UPDATE/DELETE from app DB role) specified as a migration deliverable, not just an operational recommendation? [Completeness, data-model.md §audit_events] — **PASS** — data-model.md specifies the REVOKE statement in the platform.audit_events migration description

## 5. Database Isolation

- [x] CHK027 — Is the no-cross-schema-JOIN rule enforced by both Pest Architecture Tests (PHP import analysis) AND a SQL query analysis gate (detecting raw SQL string JOINs across schemas)? [Completeness, Spec §FR-002, FR-004, Gap] — **GAP** — FR-004 mandates CI/CD validation and Pest Architecture Tests are specified; however, Pest tests analyse PHP class imports and cannot detect raw SQL strings in query builders; a financial developer using `DB::statement()` with a cross-schema JOIN would bypass this gate
- [ ] CHK028 — Is the read-model/projection strategy specified for cases where a single API response requires data from multiple modules (e.g., wallet balance + identity name + transaction history from three schemas)? [Completeness, data-model.md §Cross-Module Reference Strategy, Gap] — **GAP** — data-model.md states "no cross-schema FK, UUID references only"; it does not specify the assembly strategy (application-layer aggregation? event-sourced projections? dedicated reporting schema?); financial reporting epics need this pattern
- [x] CHK029 — Is the named-DB-connection-per-schema convention (one `config/database.php` connection per PostgreSQL schema) stated as a spec-level requirement that financial repositories MUST follow? [Completeness, Gap] — **GAP** — the named-connection pattern is in plan and research only; no FR mandates it; a financial repository author could use the default connection and accidentally address another schema's tables
- [x] CHK030 — Is the cross-module reference strategy (UUID stored without FK constraint, validated at application layer) stated as a requirement with a specific consequence (CI failure, rejected migration) if violated? [Completeness, data-model.md §Schema Ownership Map] — **PASS** — data-model.md states the rule explicitly; FR-004 mandates CI/CD validation of cross-domain data access; consequence (CI block) is specified

## 6. Outbox / Event Integrity

- [x] CHK031 — Are event ordering guarantees explicitly specified — either as guaranteed FIFO per aggregate or as explicitly NOT guaranteed (events may be delivered out-of-order)? [Completeness, Gap] — **GAP** — no requirement specifies event ordering; if `Wallet.Transfer.Completed` must be processed before a `Wallet.Transfer.Reversed` for the same aggregate, this is a financial correctness concern that is not addressed
- [x] CHK032 — Is the mechanism for idempotent event consumption (FR-053) specified — e.g., tracking processed event IDs in a `processed_events` table or enforcing unique constraints on aggregate state? [Clarity, Spec §FR-053] — **GAP → RESOLVED** — tasks.md T075b creates `ProcessedEventRepositoryInterface` with `hasBeenProcessed()` and `markAsProcessed()`; each consuming module owns its own `processed_events` table; migration template provided
- [x] CHK033 — Are Outbox records stuck in `processing` status (because the dispatcher worker crashed mid-delivery) addressed by a cleanup/timeout requirement? [Completeness, Gap] — **GAP → RESOLVED** — FR-182 added: scheduled cleanup job resets records where `status = 'processing'` AND `processing_started_at < now() - config(events.outbox.processing_timeout_seconds)` back to `pending`; `processing_started_at` column added to `platform.outbox_events` in data-model.md
- [x] CHK034 — Are correlation ID and causation ID specified as mandatory (non-nullable) fields in all integration events, particularly for financial events that must be traceable through an audit? [Completeness, Spec §FR-051, contracts/event-envelope.md] — **GAP** — FR-051 includes both fields in the event envelope; `IntegrationEventInterface` shows `causationId(): ?string` (nullable); no requirement states that financial events specifically MUST have non-null causation IDs
- [x] CHK035 — Is event delivery idempotency (Outbox dispatcher must not deliver the same event twice even if it processes the same record twice due to SKIP LOCKED race) specified as a requirement? [Completeness, Gap] — **GAP** — the Outbox status machine (`pending` → `processing` → `delivered`) prevents re-delivery if correctly implemented, but no requirement explicitly addresses what happens if the dispatcher crashes between status update and delivery acknowledgement (at-least-once vs. exactly-once delivery guarantee is unspecified)
- [ ] CHK036 — Is the DLQ alerting requirement (FR-056: "alerted") specified precisely enough to implement — including alert medium, threshold (immediately on first dead-letter? after N events?), and escalation path? [Clarity, Spec §FR-056] — **TBD/DEFERRED** — alerting medium is correctly deferred (observability backend TBD); threshold and escalation are operational decisions; the requirement is appropriately minimal for this phase

## 7. Financial Failure Modes

- [ ] CHK037 — Is the provider timeout recovery pattern (retaining financial operation in `PENDING` state and allowing safe retry without duplication) stated as an explicit spec requirement, or only as an Edge Case note? [Completeness, Spec §Edge Cases, Gap] — **GAP** — the Edge Cases section mentions "Provider timeout recovery" but no FR specifies the PENDING state requirement, the retry mechanism, or the platform contract that domain epics must implement for timeout recovery; it is currently a design note, not a requirement
- [ ] CHK038 — Is duplicate provider callback handling (provider calling back twice for the same transaction) addressed at the platform idempotency level or deferred to domain epics? [Completeness, Gap] — **GAP** — the platform idempotency framework addresses duplicate CLIENT-initiated requests; it does not address duplicate PROVIDER callbacks (e.g., payment gateway calling `/webhooks/payment` twice with the same reference); no requirement states this is a domain responsibility vs. platform responsibility
- [x] CHK039 — Is the platform behavior during Redis unavailability explicitly specified for each Redis-dependent financial function (idempotency cache, config cache, queue processing)? [Completeness, Spec §FR-046, FR-057, Gap] — **GAP** — FR-057 prohibits Redis as source of financial truth; FR-046 says Redis is a cache; but no requirement specifies the degraded-mode behavior for each function (idempotency: fall through to PostgreSQL; config: fall through to DB; queue: Horizon dead?) when Redis is unavailable
- [x] CHK040 — Are requirements specified for what happens to financial operations in-flight when a Horizon worker is killed (SIGKILL) vs. gracefully stopped (SIGTERM)? [Completeness, Gap] — **GAP** — no FR addresses the distinction between graceful shutdown (allow in-flight job to complete) and forced kill (job is lost, must be recovered via Outbox status cleanup); this affects financial operation atomicity guarantees during deployments
- [ ] CHK041 — Are DR/RPO/RTO requirements for financial data correctly deferred (consistent with FR-070)? [Completeness, Spec §FR-070] — **TBD/DEFERRED** — correctly deferred; DR/RPO/RTO remain TBD per FR-070 and constitution Principle 2

## 8. Authorization and Audit for Financial Operations

- [x] CHK042 — Is the requirement that ALL financial mutations (not just API endpoints generally) require authorization with an identified actor explicitly stated — and is anonymous financial mutation explicitly prohibited? [Completeness, Spec §FR-073, Gap] — **GAP** — FR-073 requires server-side authorization for all API calls; it does not specifically require an identified human or service actor for financial mutations; a service-to-service call with a system actor might bypass this intent
- [x] CHK043 — Are the specific financial audit action name conventions specified (e.g., `wallet.debit`, `ledger.post`, `transfer.initiate`) or are these intentionally left to domain epics to define independently? [Completeness, Spec §FR-080, Gap] — **GAP → RESOLVED** — FR-183 added: action naming convention is `{module}.{aggregate}.{verb}` in lower-kebab-case; platform-level actions enumerated (`idempotency.replay`, `idempotency.conflict`, `configuration.changed`); action vocabulary registry required in platform docs
- [x] CHK044 — Is the `before_state` / `after_state` field content specified for financial audit events — specifically whether it is a full entity snapshot, a balance-only snapshot, or a diff of affected fields? [Clarity, Spec §FR-081, Gap] — **GAP → RESOLVED** — FR-184 added: named-field diff JSON (changed fields only, not full snapshot); financial amounts in smallest-unit integers; PII pre-masked by caller (not by audit infrastructure)
- [x] CHK045 — Is the requirement that no financial operation can be executed without passing through the platform idempotency middleware (no bypass path) explicitly stated and enforced? [Completeness, Spec §FR-045, Gap] — **GAP** — FR-045 mandates idempotency enforcement at the application layer but does not specify how bypass is prevented (mandatory base controller? middleware that cannot be removed? CI check?); a developer could add a financial endpoint without the middleware
- [x] CHK046 — Is the correlation ID and actor ID preservation requirement stated explicitly for the full financial operation chain: API request → domain service → ledger post → outbox event → audit record? [Completeness, Spec §FR-087, FR-093] — **PASS** — FR-087 mandates correlation ID propagation across all application layers; FR-093 mandates end-to-end observability via correlation IDs; this covers the full chain

## 9. Architecture Extraction Readiness (Financial Modules)

- [x] CHK047 — Are the financial module interface stubs (`WalletModuleContract`, `LedgerModuleContract`, `TransactionModuleContract`) specified as Platform Foundation deliverables, following the same pattern as `IdentityModuleContract`? [Completeness, contracts/module-contracts.md §Module Stub Contracts, Gap] — **GAP → RESOLVED** — all three stubs added to contracts/module-contracts.md; FR-185 added as spec requirement; NullImplementation registration (throwing `ModuleNotImplementedException`) mandated by FR-179 and FR-185
- [ ] CHK048 — Is the synchronous vs. asynchronous communication boundary for financial operations explicitly specified — specifically which cross-module financial calls are synchronous (HTTP or in-process) vs. asynchronous (event-driven)? [Completeness, Gap] — **GAP** — the extraction seam model defines the seams; it does not define which inter-module financial calls are currently synchronous (and would become HTTP calls on extraction) vs. already asynchronous (event-driven); this boundary is critical for understanding extraction scope and latency implications
- [x] CHK049 — Is the guarantee that module extraction preserves all financial invariants (idempotency, write-once audit, no partial effects) explicitly stated, or is it only implied by the 6-seam extraction model? [Completeness, contracts/module-contracts.md §Extraction Seams] — **PASS** — the 6-seam model ensures domain logic (including financial invariants) moves with the module; only the connection string and event bus change; invariants are preserved by design
- [ ] CHK050 — Are requirements for cross-module financial read projections (how the Admin API assembles a wallet balance + transaction history + identity data response without cross-schema JOINs) specified or explicitly deferred to reporting epics? [Completeness, Gap] — **GAP** — the isolation rule prohibits cross-schema JOINs but provides no guidance on the projection assembly pattern; financial reporting and reconciliation epics will need this before implementation; the gap should be documented for E24+ epics to address
