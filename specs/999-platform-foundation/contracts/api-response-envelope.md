# Contract: API Response Envelope

**Feature**: Platform Foundation | **Version**: 1.0.0 | **Date**: 2026-08-16

All REST API responses from `/v1/` endpoints MUST conform to this envelope. No custom response formats are permitted. (FR-029, FR-030, FR-031)

---

## Success Response (Single Resource)

```json
{
  "success": true,
  "data": {
    "id": "019263a8-0000-7000-8000-000000000001",
    "type": "wallet",
    "attributes": { }
  },
  "error": null,
  "correlation_id": "019263a8-0000-7000-8000-000000000000",
  "meta": null
}
```

HTTP status: `200 OK` (retrieve) | `201 Created` (create)

---

## HTTP Status Codes

| Code | Meaning | When Used |
|---|---|---|
| `200` | OK | Successful read, update, delete |
| `201` | Created | Successful resource creation |
| `202` | Accepted | Async operation accepted (not yet complete) |
| `400` | Bad Request | Business rule violation (limit exceeded, policy violation) |
| `401` | Unauthorized | Missing or invalid authentication token |
| `403` | Forbidden | Authenticated but insufficient permissions |
| `404` | Not Found | Resource does not exist (or hidden by authz) |
| `409` | Conflict | Duplicate resource, state machine conflict |
| `422` | Unprocessable Entity | Input validation failure (field-level errors) |
| `429` | Too Many Requests | Rate limit exceeded |
| `500` | Internal Server Error | Unexpected system error |
| `503` | Service Unavailable | Degraded mode: TBD config value required, or module DB connection unavailable |

## Error Code Taxonomy (Platform Level)

These codes are defined at platform level. Domain-specific codes (e.g., `INSUFFICIENT_BALANCE`) are defined by their respective epics.

| Code | HTTP | Description |
|---|---|---|
| `VALIDATION_ERROR` | 422 | One or more input fields failed validation |
| `AUTHENTICATION_REQUIRED` | 401 | No valid authentication token provided |
| `TOKEN_EXPIRED` | 401 | Bearer token has expired |
| `TOKEN_INVALID` | 401 | Bearer token signature or claims invalid |
| `PERMISSION_DENIED` | 403 | Authenticated actor lacks required permission |
| `RESOURCE_NOT_FOUND` | 404 | Requested resource does not exist |
| `RESOURCE_CONFLICT` | 409 | Duplicate or conflicting state |
| `IDEMPOTENCY_KEY_MISMATCH` | 409 | Same key, different payload — replay mismatch |
| `IDEMPOTENCY_IN_PROGRESS` | 409 | Same key is currently being processed |
| `RATE_LIMIT_EXCEEDED` | 429 | Too many requests; `Retry-After` header included |
| `BUSINESS_RULE_VIOLATION` | 400 | Business policy blocked the operation |
| `PROVIDER_ERROR` | 502 | External provider returned an error |
| `PROVIDER_TIMEOUT` | 504 | External provider timed out |
| `TBD_CONFIGURATION` | 503 | Required configuration value is TBD |
| `SERVICE_UNAVAILABLE` | 503 | Module dependency unavailable (e.g., named DB connection refused); `correlation_id` for support |
| `INTERNAL_ERROR` | 500 | Unexpected error; `correlation_id` for support |

## X-Request-ID vs X-Correlation-ID

These two headers serve different tracing purposes and MUST NOT be conflated (FR-032).

| Property | `X-Correlation-ID` | `X-Request-ID` |
|---|---|---|
| **Origin** | Client-provided; generated by server if absent | Always server-generated; never accepted from client |
| **Format** | UUID v4 or v7 | UUID v7 only |
| **Scope** | Spans an entire business flow (multiple HTTP calls, events) | Single HTTP request only |
| **Propagation** | Propagated to downstream calls and integration events | NOT propagated; scoped to this request only |
| **Returned in response?** | Yes (`X-Correlation-ID` response header) | Yes (`X-Request-ID` response header) |
| **Client-controlled?** | Yes (client sets it to group related calls) | No (server generates it; client value is ignored) |
| **Purpose** | Correlate related operations across a distributed flow | Uniquely identify a single server-side request for log tracing |

Rules:
- If the client sends `X-Correlation-ID`, the platform MUST use that value unchanged.
- If the client does not send `X-Correlation-ID`, the platform generates a UUID v7 and uses it for the remainder of the request.
- The platform MUST generate a new UUID v7 `X-Request-ID` for every incoming request, regardless of what the client sends.
- If the client sends an `X-Request-ID` header, the platform MUST ignore it and generate its own.
- Both headers MUST appear in every API response.

## Required Request Headers

| Header | Required | Format | Notes |
|---|---|---|---|
| `Authorization` | Yes (most endpoints) | `Bearer {jwt}` | See Security Foundation |
| `X-Correlation-ID` | No (auto-generated if missing) | UUID v4 or v7 | Returned in response |
| `Idempotency-Key` | Yes (state-changing financial ops) | UUID v7 | Required per FR-033 |
| `Content-Type` | Yes (POST/PATCH) | `application/json` | |
| `Accept` | No | `application/json` | |

## Required Response Headers

| Header | Value | Notes |
|---|---|---|
| `X-Correlation-ID` | `{uuid}` | Always present, mirrors request or generated |
| `X-Request-ID` | `{uuid}` | Server-generated per-request identifier |
| `Content-Type` | `application/json; charset=utf-8` | Always |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` | HTTPS only |
| `X-Content-Type-Options` | `nosniff` | |
| `X-Frame-Options` | `DENY` | |
| `Content-Security-Policy` | (TBD by security team) | Placeholder |
| `Deprecation` | `true` | Present only on deprecated endpoints |
| `Sunset` | `{ISO 8601 date}` | Present only on deprecated endpoints |
| `Retry-After` | `{seconds}` | Present only on 429 responses |

---

## API Versioning

- Current version: `/v1/`
- All endpoints prefixed: `/v1/{module}/{resource}`
- Deprecation: Deprecated endpoints must include `Deprecation: true` and `Sunset:` headers.
- Version negotiation: Content-type versioning is NOT used; URL versioning only.
- Breaking changes require a new major version (`/v2/`).
