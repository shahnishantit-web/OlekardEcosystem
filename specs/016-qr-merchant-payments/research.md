# Research — E16 QR & Merchant Payments

## QR Payload Format & Signing

**Decision**: HMAC-SHA256 over a canonical JSON representation of the payload fields; signature is embedded as a `sig` field; the whole signed object is Base64URL-encoded to produce the scannable QR string.

**Rationale**: HMAC-SHA256 is fast, well-supported in PHP (`hash_hmac()`), and sufficient for a closed-loop platform where only the server verifies payloads. Embedding `sig` inside the payload object avoids a multi-part format. Base64URL produces a compact, URL-safe string for QR encoding. The signing key is never embedded in the payload (FR-E16-014).

**Signed fields**: `type`, `merchant_id`, `currency`, `amount` (nullable), `nonce`, `expires_at` (nullable), `merchant_ref` (nullable).
**Not signed**: `label` (display-only metadata stored in DB, not part of payment identity).

**Signing steps**:
1. Build canonical array of signed fields (sorted keys, null values excluded).
2. `$json = json_encode($canonical, JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES | JSON_THROW_ON_ERROR)`.
3. `$sig = rtrim(strtr(base64_encode(hash_hmac('sha256', $json, $key, true)), '+/', '-_'), '=')`.
4. Append `sig` to the payload array.
5. `$qrString = rtrim(strtr(base64_encode(json_encode($payloadWithSig)), '+/', '-_'), '=')`.

**Verification**: Decode Base64URL → JSON; extract and remove `sig`; re-sort remaining fields; recompute HMAC; constant-time compare (`hash_equals`).

**Alternatives considered**: JWT (unnecessary complexity for a platform-internal token), EMVCo MPQR (requires licensed parser; overkill for closed-loop), asymmetric signing (RSA/ECDSA — unnecessary since verification is server-only).

## Key Rotation Strategy

**Decision**: Single active signing key stored in environment-backed config key `qr.signing_key`. On rotation, the old key is replaced. Dynamic QRs expire naturally within their TTL. Static QRs must be re-generated by merchants after rotation (per spec FR-E16-014). A key rotation should trigger a merchant notification via E17.

**Rationale**: Key versioning (storing N keys by ID) adds complexity and risks the key-ID leaking information. Given dynamic QRs have short TTLs and static QRs require explicit re-generation anyway, a single active key is sufficient for this epic.

**Alternatives considered**: Versioned keys with key-ID in payload (rejected — spec prohibits key embedding; key-ID could also leak information).

## QR Reservation Mechanism

**Decision**: Dual-layer enforcement using pessimistic locking.

1. **At confirmation time**: `QrPaymentService::confirm()` acquires `SELECT FOR UPDATE` on the `qr_codes` row before any state change. Logic: if `status = reserved AND reserved_until >= now()` → 409 (QR locked); if `status = reserved AND reserved_until < now()` → unlock (set `active`) and allow; if `status = active` → transition to `reserved` with `reserved_until = now() + reservation_ttl`.
2. **Background cleanup**: `ReleaseExpiredQrReservationsJob` bulk-updates rows where `status = reserved AND reserved_until < now()` to `active`. Runs every 60 seconds.

**Rationale**: The at-confirmation lock is the correctness mechanism. The background job is cleanup only. Without both, expired reservations could persist indefinitely if no customer re-scans.

**Alternatives considered**: Only background job (insufficient — stale reserved rows block customers until next run); only at-confirmation check (insufficient — rows never cleaned up without re-attempt).

## Merchant Entity Reference

**Decision**: Read merchant data (display name, merchant wallet ID, active status) via `MerchantReadServiceInterface` from the merchant module (established by E12). The QR module does not own or replicate merchant data.

**Rationale**: Constitution P7 — domain boundaries are explicit and extraction-ready. QR is a consumer of the Merchant domain.

---

## Fee Calculation

**Decision**: Apply a configurable fee read from `ConfigurationServiceInterface` at payment time. Pattern follows E09 Wallet-to-Wallet Transfer: triple-leg journal (customer debit for principal + fee, merchant credit for principal, platform fee wallet credit for fee).

**Config keys**: `qr.payment.fee_type` (`flat` | `percent`), `qr.payment.fee_value`, `platform.fee_wallet_id`.

**Rationale**: E21 Fees & Pricing is not yet implemented. Runtime config achieves P3 configurability without that dependency. The fee wallet ID is resolved from config, same pattern as prior epics.

**Alternatives considered**: Zero fee for MVP (rejected — fee capability must be present from launch); hardcoded rate (rejected — violates Constitution P3).

## Step-Up Authentication

**Decision**: Constitution P5 is authoritative — `auth.step_up_threshold = 10000` BWP, runtime-configurable. `QrPaymentService` reads this threshold via `ConfigurationServiceInterface`. Payments at or above threshold require a valid step-up token before wallet debit; token is validated by the existing `StepUpAuthService` (E03).

---

## Concurrency Control

**Decision**: Pessimistic row lock (`SELECT FOR UPDATE`) on `qr_codes` during reservation check + transition. Idempotency enforced via `UNIQUE` constraint on `qr_payment_transactions.idempotency_key` + database-level conflict detection.

**Concurrency tests required (Constitution P4)**:
- Test A: Two customers confirm the same dynamic QR simultaneously → exactly one succeeds, one gets 409.
- Test B: Identical `Idempotency-Key` submitted twice in parallel → exactly one transaction created, second returns original response.

---

## Module Placement

**Decision**: `App\Modules\Qr` — new module following the established modular-monolith pattern. PostgreSQL schema: `qr`. Laravel service provider: `QrServiceProvider`.
