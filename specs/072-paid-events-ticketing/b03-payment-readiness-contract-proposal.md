## Proposed contract additions for review

1. **Finance-owned event currency assignment.** Keep the existing draft field null until an authorized Finance/platform actor assigns a code that is active and supported. The authoritative record should identify organisation/event, currency code and precision/version, assigning/approving actor, approval reference, policy version and timestamp. Enforce the already-recorded lock after the first order or active hold. Define how an approved currency deactivation is handled without silently converting existing orders.
2. **Actor-free event publication readiness.** Add a typed Payments readiness query/result for event context: organisation ID, event ID, event country/jurisdiction, canonical purpose type and module key (both to be registered by owners), event currency, sellable category price bounds, and required capability only if the approved product contract requires one. Result should say eligible/ineligible and return non-secret reasons, eligible method/instrument classes, evaluated-at time and provider/account configuration versions. It must not use a customer actor or wallet balance. It should be rechecked at publication and sales resumption; readiness does not create a quote or guarantee every customer can pay.
3. **Customer-specific checkout remains separate.** At checkout, Events derives the current approved event/category, held quantity, price, currency, organisation, order reference and country context server-side, then calls existing `getAvailableOptions(OptionsQuery)` with the authenticated customer and exact payable amount. This stage may consider that customer's wallet balance. Client-supplied amount, tenant, provider status and payment result are not authoritative. If total/fees change, require new confirmation under the recorded P25 rule.
4. **Shared intent and confirmation.** Events later invokes existing `createPaymentIntent(PaymentIntentRequest)` with a P25 purpose resolver that derives price/currency from the authoritative order/hold. The hold and quote/payment-attempt expiry must be linked by the approved contract. Events consumes the durable `payment.confirmed` event idempotently and issues an entitlement once. Unknown outcomes remain unresolved. No event-level readiness result is proof of customer payment.
5. **No invented freshness value.** Owners must choose the readiness result freshness/expiry or require a live query at each gated transition. The proposed response carries `evaluated_at` and configuration versions so a stale result can be detected; this proposal sets no TTL.

## Ownership and acceptance

- **Finance + MultiCurrency/Platform:** currency assignment authority, active supported code/precision, approval provenance and currency lifecycle.
- **Payments/ProviderRegistry:** typed actor-free event readiness contract, canonical eligibility fields and freshness/version semantics; preserve existing checkout filtering.
- **Events:** derives approved event/category/order context and invokes shared contracts; owns no provider API, balances or ledger.
- **Acceptance:** draft currency stays null absent approved assignment; publication readiness uses server-built event context and does not depend on arbitrary customer wallet balances; checkout uses current server-authoritative price/currency/quantity and customer-specific options; absent readiness/contract denies publication and sales; provider configuration never becomes proof of certification; P24/live processing remain disabled.

### Business choices requiring approval

1. **Category coverage at publication:** Option A: at least one paid category has a configured payment path (other categories may be unsellable); Option B: every paid/sellable category price has at least one configured path. **Recommendation: B**, so publication cannot expose an unsellable paid tier; this can restrict sales if provider amount bounds differ by category. This remains unapproved.
2. **Wallet-only event readiness:** Option A: an enabled wallet mechanism counts as a configured path even though customer balance is unknown; Option B: wallet alone does not satisfy publication readiness without a non-wallet configured method. **Recommendation: A only if readiness is expressly labelled ìconfigured path existsî and checkout remains customer-specific.** Consequence: an individual customer with no wallet or insufficient funds may still have no usable option. This remains unapproved.
3. **Currency lifecycle after lock:** Option A: deactivate currency for new events and pause affected existing event sales while preserving orders; Option B: keep sales on using the captured assignment precision while blocking reassignment; Option C: require Finance-approved replacement/conversion process. **No recommendation recorded here** because customer balances, orders, provider capability and accounting treatment require Finance evidence. No automatic conversion is authorized.
4. **Readiness freshness:** No cache and live re-evaluation at publish/resume is the technical recommendation above. If owners require caching, specify a maximum age; no TTL is otherwise proposed.

### What actor-free readiness establishes ó and does not establish

It can establish that, at a recorded time and for the exact server-derived event/currency/category context, the approved event-level rule found at least one currently configured shared method/provider account passing Registry's static eligibility checks. It can support publication gating and identify a failed configured condition.

It cannot establish that every customer can pay; it has no authenticated customer, wallet balance, account-specific restrictions or payment instrument. It cannot establish provider uptime, network reachability, certification, real initiation success, callback correctness, settlement/refund capability, guaranteed capacity, or a future payment outcome. It must never be displayed as ìall customers can payî or ìprovider certified.î Unknown payment outcomes remain unresolved under shared Payments.

## Accepted development decisions and implementation status ‚Äî 2026-10-28

The following are accepted P25 product/design directions for development. They are not Finance/Security approval, provider certification, or production/sales authorization.

- Readiness must cover **every currently sellable paid category independently** at its authoritative category price and event currency. Missing/unsupported category coverage fails. Fees, tax, discounts and totals remain outside this readiness result under B-06.
- A configured Wallet path may satisfy static method coverage. The result and customer experience must say wallet-only where applicable; it never asserts customer balance. Checkout remains customer-specific and mandatory.
- Currency is assigned by a Finance-authorized, event-scoped `events.currency.assign` grant and is recorded with assigning actor, approval reference, policy version, authoritative currency precision and the currency definition's actual `updated_at` value. This timestamp is provenance, not an invented version. First durable order or inventory hold locks code and precision; expiry/cancellation does not unlock. After lock, reassignment and conversion are rejected.
- If current currency is inactive or precision differs from the snapshot, readiness and new checkout/sales must fail, records retain purchase-time precision, and an operator-review issue is recorded. This code records the issue and rejects new inventory holds. It does not cancel/refund/rewrite. There is no P25 durable order/checkout integration yet, so the order-lock hook exists as a transaction contract but has no order caller.
- Static readiness uses `StaticEligibilityContext` and `EventStaticReadinessQuery`, neither includes a customer actor. It does not cache and returns per-category coverage, safe reason codes, evaluation time, and actual provider/account configuration values. It is a reusable Payments service, not wired as production Events publication readiness while canonical event context is missing. Existing Events readiness remains deny-by-default. Customer checkout still uses the existing actor-specific `OptionsQuery` and exact server-derived amount.

### Remaining B-03 technical and operational boundaries

- The `events.currency.assign` catalog entry has no automatic role grant. Writes require the Identity permission and exact live Events event assignment, plus active organisation membership. The Finance-scoped assignment-administrator class already controls delegation of this permission. No operational assignment/bootstrap was created or run.
- Currency, assignment provenance and first-hold lock are persisted in Events migrations 100009/100010. The first-hold race is serialized on the event row. Currency-definition edits live in MultiCurrency's connection; current contracts expose lookup but no cross-module transaction/lock protocol. A concurrent currency precision deactivation/update can race the read-and-lock unless MultiCurrency supplies an authoritative snapshot/lock contract. New holds recheck the current row on every request and fail closed, but a durable cross-connection atomicity guarantee is not claimed.
- Publication and sales resumption call the existing readiness contract (resume now reevaluates the immutable approved snapshot), but the production implementation remains `DenyEventPublicationReadiness`. Publication/sales remain unavailable until canonical context and provider configuration can be evaluated and independent reviews/authority gates pass.
- A `durable_order` currency-lock hook is provided for a future order transaction. It must be invoked under the same `community_services` transaction and event-row lock before inserting the first order. No T010 order table/checkout caller exists. This hook does not make T010 complete.
- Provider/account config versions are exposed only when present: `metadata_version`, `config_version`, and `active_config_version_id`. Currency definition `updated_at` is a timestamp, not a version. No readiness cache is used.
