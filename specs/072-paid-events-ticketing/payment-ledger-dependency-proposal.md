**Status:** bounded P08 development scope authorized and implemented for development; operational accounting decisions, independent review and live readiness remain unapproved. No duplicate package was created. P08 code/evidence checkpoint is recorded in `specs/057-ledger-ack-fulfilment/`.

### AD-09: external/bank payment path

AD-09 remains **UNRESOLVED / AWAITING FINANCE EVIDENCE** in `docs/architecture/decisions/ADR-E48-003-accounting-decisions.md`. The exact source cited by the ADR is now verified at `docs/sources/Olekard_Shared_Payment_Architecture_v1.1.docx`; the accessible v1.1 document explicitly says bank names are placeholders and no bank API/live provider contract was inspected. It does not contain the required AD-09 account mapping. The decision concerns the bank settlement receivable debit and unresolved credit account. `postLedgerAcknowledgement()` continues to skip attempts with `wallet_hold_id === null`; accounting remains `pending_ledger`, with no `payment.confirmed` event or Events confirmation evidence. A succeeded external attempt therefore cannot issue a P25 ticket.

**Required before accepting an external method:** Finance Lead's written AD-09 decision must identify the approved debit/credit account mapping, entity/custody meaning, currency and transaction classification, and effective approval evidence. Payments/Ledger must implement and test a balanced, idempotent posting path for that method and its repair path. The provider adapter must supply independently verifiable capture facts (including actual captured amount/currency and provider reference) through the approved callback/query contract. Until then, preserve a captured attempt as captured and accounting-pending; do not fabricate a journal, emit authoritative confirmation or issue a ticket. Do not invent provider APIs or use a development mock as evidence.

Wallet path is distinct: P08 uses the payer wallet pocket debit and configured `payment.credit_account_{currency}` credit. AD-08/configuration and its Finance evidence must be checked for the method before calling it financially ready. This proposal does not infer that wallet accounting approval resolves AD-09.

## 2. Proposed evidence and state protocol

1. **Durable capture fact:** P06/Payments stores the provider-verified outcome against the exact attempt. It preserves the actual captured minor amount, currency and provider reference; the immutable intent supplies intent ID, purpose/order reference, organisation, purchaser, requested amount and currency. A mismatch or excess capture remains an accounting/reconciliation fact and is not silently converted into ticket authorization.
2. **Ledger acknowledgement:** P08 calls Ledger with the existing stable key `payment:{payment_intent_id}:ack` and transaction reference equal to the intent ID. Ledger returns an ID only after its journal transaction commits. The Ledger query contract verifies posted status, exact reference/key/currency, balanced lines and amount. If an accounting account decision or posting is missing, Payment remains `pending_ledger`; no confirmation event is emitted.
3. **Payment confirmation evidence:** In one Payment DB transaction, Payment locks/reloads intent and succeeded attempt; stores `ledger_journal_id`, `accounting_status=ledger_posted`, and an immutable evidence version; and inserts `payment.confirmed` in the same connection's outbox. Event versioned payload includes payment/attempt IDs, purpose type/reference, organisation, payer, requested and captured amount/currency, verified journal ID, `accounting_status=ledger_posted`, correlation ID and occurrence time. The event is a wake-up/delivery record, not authority to skip Events' order comparison or Payments/Ledger evidence query.
4. **Consumer verification:** Events invokes a typed, service-authenticated Payment confirmation-evidence contract, scoped to `events`/`paid_event_ticket` and the expected order reference. Payment verifies immutable intent purpose/reference, exact organisation/payer, succeeded attempt, capture amount/currency, `ledger_posted`, and Ledger's posted-journal evidence. Events compares every field with its locked order/version/hold snapshot. No client-supplied values override these sources. The current actor-only `getPaymentStatus()` must not be widened as a workaround.
5. **Events issuance transaction:** Events persists inbox/dedup evidence, one issuance row and one distinct entitlement/credential per purchased ticket in its own durable transaction, guarded by unique intent/order/allocation and per-entitlement keys. It records issuance state independently of payment, accounting, refund, settlement and payout. Replayed or out-of-order events query authoritative current evidence; duplicate/outdated events cannot regress either service's state. A verified payment fact arriving after hold expiry is not assigned a financial disposition by this contract; P25 T004 late-capture policy remains required.
6. **Acknowledgement:** Only after the durable Events ticket set commits does Events call the Payment fulfilment-ack contract with intent, purpose/order, stable acknowledgement idempotency key and durable issuance reference. Payment accepts only a matching succeeded, `ledger_posted` intent and makes `pending → fulfilled` idempotently. It never changes `fulfilled` or another terminal state back to pending. Do not mark transient Events issuance failure terminal; Events owns retry/quarantine and repair state. A pre-existing terminal Payment fulfilment state is not overwritten; surface a conflict for operator reconciliation.
7. **Recovery:** If Ledger committed but Payment's accounting/outbox transaction did not, P08 retry reuses the same Ledger idempotency key and obtains the same journal; it then commits the evidence and one outbox row without charging again. If Events committed issuance but acknowledgement or outbox delivery response was lost, redelivery finds the durable Events dedup/issuance record and retries only the idempotent acknowledgement. If either side is terminal, inconsistent or unknown, do not rewrite it; retain evidence and route to the owning reconciliation queue. Dead-letter replay remains an operator action with audit.

State ownership remains separate: Payment intent/attempt state owns capture outcome; Payment accounting state owns ledger acknowledgement; Events issuance state owns entitlement creation; Payment fulfilment acknowledgement is a cross-module receipt only. Settlement and payout are not implied by `payment.confirmed` or `fulfilled`.

### Existing package decision

Do not create another Payment/Ledger/Outbox package. Resume existing P08 first because it owns `PaymentOrchestrationService::postLedgerAcknowledgement()` and `PaymentConfirmedEvent`; scope the new typed evidence and acknowledgement contracts there and involve P06/P02 owners for state/schema/API changes. Resolve AD-09 with Finance before implementing external/bank accounting. Then verify P11's existing delivery checks and add Events' own consumer idempotency as part of P25 T010/T011. P18 is payout-only and is not a dependency for order, issuance or admission.

## 4. P08 implementation checkpoint and remaining acceptance evidence

Targeted P08 feature and repair tests pass 13/13 (31 assertions), Ledger evidence tests pass, and P11 listener dedup passes. The P08 source path/version discrepancy is resolved: `docs/sources/Olekard_Shared_Payment_Architecture_v1.1.docx` exists and confirms architecture but no bank APIs/mappings. The migration has not been applied to the shared local schema due the legacy Identity schema/history conflict. Database-backed acknowledgement, true crash injection and full P08/P11 Docker quickstart remain unverified. See P08 tasks/research for actual run details.

P25 must still build an authoritative Events order and transactional issuance/inbox. The P08 acknowledgement trusts the authenticated Events service's attestation that its durable fulfilment reference exists; it cannot verify a future Events transaction. No resolver or placeholder was registered.

- Contract tests map every field above to immutable authoritative records and reject wrong/missing intent, attempt, purpose/order, organisation, purchaser, captured amount, currency, accounting state, journal ID, journal status, transaction reference, idempotency key or balanced amount.
- Wallet test: journal committed and verified before Payment sets ledger-posted or writes confirmation outbox; all evidence fields agree; attempt records journal ID; unsupported/missing AD-08 configuration emits no confirmation.
- AD-09 negative test: succeeded external/bank attempt remains captured plus `pending_ledger`; no journal/confirmed event/Events issuance. No fake accounts/provider response.
- AD-09 positive test only after written Finance decision: approved external mapping posts one balanced journal; repair/replay yields same ID; confirmation/outbox emitted once. Test evidence cites the Finance decision and approved source contract; this is not live provider certification.
- Crash injection after Ledger commit/before Payment commit; retry reuses the same ledger idempotency key and produces one evidence row/outbox event without a second charge or journal.
- Separate PostgreSQL sessions for duplicate/reordered outcome and concurrent repair; exactly one accounting event. Payment terminal states are never reversed.
- Outbox delivery crash after dispatch/before delivery mark, retries, max-attempt dead-letter, authorized replay and audit. P25 Events inbox/replay delivers at least once but creates one entitlement set.
- Events contract tests prove mismatch or missing evidence creates no ticket, duplicate/out-of-order event creates no duplicate/regression, and the fulfilment acknowledgement is sent only after durable issuance. Retry acknowledgement after lost response is idempotent; terminal states are not rewritten.
- Customer/module boundary tests prove the actor-scoped customer status route cannot substitute for the internal authenticated contract and no other tenant/purpose can query evidence.
- Existing P08 T027/T028 quickstart and P11 T028–T031 checks are run/recorded; applicable PHPStan, migration/schema and full relevant feature tests pass in a schema-complete environment. The previous P08/P11 artifacts mark Docker-gated checks incomplete; do not claim verification without executing them.

## 6. Decisions, external evidence, and independent gates

- **Business/accounting decision:** Finance Lead must resolve AD-09's bank settlement debit and credit accounts, currency/account classification, custody/entity meaning, and effective approval record. AD-08 wallet credit account authority/configuration must separately be verified for wallet posting. Neither is supplied by P25 product approval.
- **Other P25 Finance/tax decisions remain separate:** fee payer/schedule, tax treatment and rounding, cancellation/refund, late capture and currency-drift recovery. They are not answered here.
- **External evidence:** accessible architecture v1.1 source or Finance's written AD-09 decision; provider-specific verified capture/currency/reference and certification before any live method claim; no provider API or credential may be invented.
- **Independent review:** Finance review of accounting mappings; Payments/Ledger contract review; Security review of service authentication and tamper resistance; Events/Privacy review of purchaser binding and evidence minimisation. Product approvals and automated tests do not satisfy these reviews. Existing governance does not name/appoint reviewers.
- **Operations:** name the owner/SLA for `pending_ledger`, reconciliation exceptions, dead-letter confirmation events and P25 issuance conflicts; retain event, intent, attempt, journal, outbox and correlation IDs. No manual status override.

## 7. P25 impact and development boundary

The contract is required for order-to-payment integration, confirmation-based ticket issuance, issuance repair after delayed delivery, and any Payment fulfilment acknowledgement. It is not required for already implemented event authoring/review, inventory-hold concurrency, currency coordination, aggregate report design, or the standalone credential primitive. Single-entry online admission implementation depends on durable ticket storage/issuance, not P18 payout; re-entry remains disabled. Customer display/credential replacement depends on Events persistence and Identity step-up/recovery wiring, not live provider certification. Fee/tax/rounding decisions still block payable quote/order totals; refund/cancellation/late-capture policies block only those corresponding flows. Missing live provider certification blocks that live method, not isolated domain development with clearly labelled test fixtures.

P08 contract code is available for development fixtures. No Events payment purpose resolver, event publication, checkout/sales, P24, production bootstrap or deployment is enabled. P25 may integrate only after durable Orders exist, policy/Finance gates are approved, and schema-safe verification is available.
