Permission slugs follow `{module}.{resource}.{action}` (examples `admin.user.create`, `configuration.policy.update`). `IdentityModuleContract::hasPermission(actor, slug)` resolves global permissions through global user-role and role-permission tables and caches by actor; `RequirePermissionMiddleware`/`AuthorizationGuard` enforces a slug and records denied attempts. ## Separation-of-duties answers and enforcement gaps

- **May an author review their event?** No. A-02 prohibits every contributor to the submitted version from approving either event review or Finance price review. P25 now records cumulative version contributors and rejects them in both approval paths. Event reviewer and Finance price approver must also be different people. These are product decisions, not independent Security or Finance approval.
- **Who resumes sales?** The operator needs an explicit event-scoped grant. A-03 accepts this principle; exact mapping and grant/revoke authority remain proposed.
- **How is scanner authority revoked?** Next online scan after revocation is denied; scan/revoke races follow commit order. Proposed implementation stores the operator-to-gate assignment in Events and checks it in the same transaction as the scan. Do not rely on the global Identity permission cache alone.
- **How is re-entry counted?** Settled: only returns count, not initial admission. The organiser configures the event-specific allow/deny policy and numeric limit subject to review; exit is recorded online. D-02 is only the missing numeric maximum return count. It does not reopen counting semantics or configuration authority.

## Ownership assessment and proposed grant model

E04/Identity owns the global role-permission catalogue, `hasPermission(actor, slug)`, token claims and permission cache. E04 explicitly excludes fine-grained row-level/ABAC authorization. Events owns event/gate resources and LC07/section 2 assigns it event operations and admission. The proposed compatible design is a two-part check: Identity confirms the actor has the coarse `events.*` capability; Events checks the exact organisation/event/gate assignment against its own state. This avoids cross-schema joins and keeps resource ownership with Events. Global `admin`, `agent`, `customer` roles and active organisation membership alone never authorize an Events action.

Proposed scope rules: (1) organisation-scoped `events.event.create` permits creation only and does not inherit to a new event; (2) event permissions match one exact event; (3) event scope does not inherit to gates; (4) `events.gate.assignment.manage` is a narrow delegation exception that may assign/revoke only `events.gate.validate` for gates within that event; (5) no wildcard, global-admin, service, support or break-glass bypass; (6) Events validates event/gate-to-organisation relationships server-side; (7) gate assignment and scan/revocation serialize in one Events transaction to preserve commit-order behavior. These are proposals pending A-03 and owner review.

This design does not require changing Identity's `hasPermission` contract. The accepted P25 implementation uses Events-owned assignments and did not start an E04 package. No concrete contract limitation was found. The conditional E04 extension in `authorization-dependency-proposal.md` is not currently required and must only be reconsidered if a specific contract limitation is demonstrated.

## Development decision update — 2026-10-28

The accepted development permission mapping is enforced with E04's registered coarse permission plus an Events-owned exact assignment. Global admin and organisation membership alone are insufficient. Assignment administration requires an explicit organisation/Finance authority record. Finance permissions are restricted to separately designated Finance administrators; other organisation/event assignments require the non-Finance designation. Event gate managers need their event-scoped `events.gate.assignment.manage` permission and can create gates and delegate/revoke only `events.gate.validate` for active gates of that exact event. No role grants are created automatically. These are product/design decisions and implementation evidence only; independent Identity/Security/Finance/Privacy reviews remain outstanding.

Bootstrap uses two distinct active organisation members with explicit bootstrap-approval permission plus an explicitly authorized operator and target permissions. The command is registered but not executed. The platform cannot verify the supplied approval-reference document itself; operational bootstrap remains blocked pending independently verified evidence. Revoking an administrator stops subsequent grant/revoke operations immediately; prior grants retain issuer provenance and require separate authorized revocation. No cascade is applied.
