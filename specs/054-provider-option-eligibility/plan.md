# Implementation Plan: P05 — Provider Registry and Option Eligibility

**Branch**: `054-provider-option-eligibility` | **Date**: 2026-10-21 | **Spec**: [spec.md](./spec.md)

## Summary

P05 extends the existing Payment module's provider registry with an ordered 8-stage eligibility pipeline, an installed-adapter allowlist, account configuration versioning, attempt-level version snapshots for safe historical resolution, structured capability/instrument enums, display metadata fields, and an admin eligibility preview API. All work is additive to the existing `payment_providers` / `payment_provider_accounts` tables and the `ProviderRegistryService` / `PaymentProviderAdminService` application services.

## Technical Context

**Language/Version**: PHP 8.4, Laravel 11

**Primary Dependencies**: Eloquent ORM, Laravel DB transactions, existing `PaymentProviderRepositoryInterface`, existing `PaymentConfigChangeDraftModel`, Platform Config service (`PlatformConfigurationService` or equivalent), Audit service (`AuditServiceInterface`)

**Storage**: PostgreSQL — `payment` schema. New columns on `payment_provider_accounts` and `payment_attempts`. No new tables required.

**Testing**: PHPUnit 11 via `./vendor/bin/phpunit`. PHPStan level 8.

**Target Platform**: Laravel API server (same as P01–P04)

**Performance Goals**: Option discovery response < 100 ms for ≤ 20 registered accounts. Eligibility preview < 500 ms.

**Constraints**: All financial mutations remain idempotent. No direct balance mutations. No URL columns added (E25 owns callback ingress — `callback_url` validation enforced, not removed for backward compat). PHPStan level 8 must remain at 0 errors on modified files.

**Scale/Scope**: 6 user stories, ~70 tasks. Backend only (no Admin UI changes in P05 scope — admin API endpoints are sufficient).

## Phase 0: Research

All necessary research is derivable from the existing codebase. No external unknowns.

### Decision: EligibilityPipeline as a separate service (not embedded in ProviderRegistryService)

- **Decision**: Extract the ordered eligibility stages into `EligibilityPipeline` that returns `EligibilityResult[]` per account.
- **Rationale**: `ProviderRegistryService` becomes a thin coordinator; the pipeline is independently testable; admin preview reuses the same pipeline to return all accounts with eligibility annotations.
- **Alternative rejected**: Embedding all 8 stages inside `discoverOptions()` — makes unit testing each stage boundary awkward and prevents preview reuse.

### Decision: AdapterAllowlistConfig reads from platform config, not database

- **Decision**: A `AdapterAllowlistConfig` infrastructure class reads `payment.adapter_allowlist` from `PlatformConfiguration` (or falls back to `config('payment.adapter_allowlist', ['olekard_wallet', 'mock_bank'])`).
- **Rationale**: Allowlist changes are infrequent operator-level decisions; reading from a config file/platform config avoids adding a new DB table while remaining configurable.
- **Alternative rejected**: Separate DB table `payment_adapter_definitions` — over-engineered for the current number of adapters (2). Can be promoted to a table in a future P-series package.

### Decision: `callback_url` column kept but validated as must-be-null on draft submission

- **Decision**: Do not drop the `callback_url` column (would break P02 migration chain). Add a validation rule in `PaymentProviderAdminService::validateDraftPayload()` that rejects any non-null `callback_url` in a change payload.
- **Rationale**: The column exists for future E25 integration. Operator data cleanup happens via the admin UI. Dropping the column is a destructive migration.

### Decision: Optimistic locking for concurrent draft approvals

- **Decision**: Draft record stores `account_config_version_at_draft_time`. Approval reads current `config_version` in a transaction; if different → reject with `CONFIGURATION_VERSION_CONFLICT`.
- **Rationale**: Pessimistic locking (SELECT FOR UPDATE through the whole approval process) holds a lock for too long. Optimistic locking is standard for low-contention config workflows.

### Decision: `provider_account_version` is nullable for backward compat

- **Decision**: Add `provider_account_version INTEGER NULL` to `payment_attempts`. New attempts populate it. Pre-P05 attempts have null and are unaffected.
- **Rationale**: Cannot retroactively determine the correct version for historical attempts. Null is a correct representation of "version unknown (pre-P05)".
