# Implementation Plan: P21 — Admin Finance Dashboard & Operations Screens

**Branch**: `068-admin-finance-dashboard` | **Date**: 2026-10-26 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/068-admin-finance-dashboard/spec.md`

## Summary

P21 delivers the Next.js admin UI layer for payment finance operations, consuming existing backend APIs from P15–P19 (E62–E66). Scope: scoped finance dashboard with KPI tiles and fulfilment backlog (US1), end-to-end intent investigation timeline (US2), refund approval and payout queues with maker-checker gating (US3), disputes and reconciliation exception management (US4), and filterable financial reports with async CSV export (US5). Two thin backend additions are required: a dashboard-summary aggregation endpoint and an admin intent timeline endpoint.

## Technical Context

**Language/Version**: TypeScript 5 / Next.js 14 App Router; PHP 8.4 (for 2 new thin Laravel controllers)

**Primary Dependencies**: React + TanStack Query (React Query v5), Tailwind CSS, shadcn/ui, jest@29 + React Testing Library, existing `PaymentApiClient` in `lib/api/payment.ts`

**Storage**: N/A (UI reads only); 2 new read-only Laravel controllers query existing payment tables

**Testing**: Jest + React Testing Library (frontend); PHPStan level 8 + feature tests (backend)

**Target Platform**: Admin web app (desktop-first); API accessed through existing Docker stack

**Project Type**: Next.js admin portal pages + 2 thin Laravel backend controllers

**Performance Goals**: All list screens load in < 2 seconds for up to 1,000 rows (SC-002)

**Constraints**:
- Zero credentials/secrets rendered in any response or UI element (SC-004, FR-020)
- Currency totals MUST be separated — never aggregated cross-currency (SC-006, FR-015)
- Approve/reject controls MUST NOT render for users without the correct permission (FR-006, SC-005)
- Controlled replay uses original operation IDs; MUST NOT invent success (FR-010)
- 2 new backend endpoints MUST follow existing route/controller conventions (thin controller, service layer)

**Scale/Scope**: ~11 new Next.js page routes, 10 new shared components, 2 new backend controllers, ~8 new TypeScript hooks, extension of `PaymentApiClient`

## Implementation Notes

### Backend: DashboardSummaryAdminController
- Query: count intents by status for today (UTC) using `payment_intents` table
- Query: sum `amount_minor` grouped by `currency_code` for today's captured/fulfilled intents
- Query: count captured intents with no matching `payment_fulfilment` record (backlog)
- All 3 queries run within the `payment` DB connection; no cross-module join
- Response: `{data: {volume_by_currency: [], attempt_counts_by_status: {}, fulfilment_backlog_count: N, fetched_at: ""}}`

### Backend: PaymentIntentTimelineAdminController
- Load intent from `payment_intents` table via existing repository
- Load attempts from `payment_attempts` table (ordered by `submitted_at`)
- Load pending-accounting flag from `payment_pending_accounting` (if exists)
- Load ledger journal refs from `ledger_journals` table WHERE `reference_id = intent_id`
- Map journal lines to `{type, account_name, amount_minor, currency_code}` — account names from `ledger_accounts` display_name, NOT raw IDs
- Strip `callback_secret_reference` and provider credential fields from attempt data
- Response uses `payment.intents.admin` permission middleware

### Frontend: Permission checks in UI
All screens use `const { hasPermission } = useAuth()` for rendering controls. The pattern:
```tsx
{hasPermission('payment.refunds.approve') && (
  <ApproveButton ... />
)}
```
This supplements (does not replace) server-side enforcement. If the server returns 403, the hook catches and shows inline error.

### Frontend: Idempotency keys for approval actions
Approve and reject actions generate a client-side UUID v7 as `Idempotency-Key` header per action instance. The hook stores the last-used key to detect retries of the same action.

### TypeScript: ApiResponse shape
All new hooks must use `res.data as unknown as T` pattern (not `res.data.data`) since the ApiClient returns the raw JSON body. See `useProviders.ts` fix from P20 for the correct pattern.

### No new design tokens
All new components use existing tokens from E35/E36. `CurrencyAmount` should check if it already exists in the shared component library before creating a new one.
