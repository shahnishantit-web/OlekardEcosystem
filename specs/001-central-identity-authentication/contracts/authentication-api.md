# Authentication API Contract — E01 Central Identity & Authentication

**Feature**: `001-central-identity-authentication` | **Base path**: `/v1`

All responses use the Platform Foundation envelope. All requests must include `X-Correlation-ID` (generated by the client; middleware echoes it). All error codes are E01-specific prefixes on the platform error taxonomy.

---

## Common Headers

| Header | Required | Notes |
|---|---|---|
| `Content-Type` | Yes (POST/PUT) | `application/json` |
| `X-Correlation-ID` | Yes | UUID; echoed in response |
| `X-Idempotency-Key` | Conditional | Required on state-changing operations |
| `Authorization` | Conditional | `Bearer <access_token>` for authenticated endpoints |

---

## Common Error Response Envelope

```json
{
  "success": false,
  "error": {
    "code": "IDENTITY_ERR_CODE",
    "message": "Human-readable message",
    "trace_id": "uuid"
  }
}
```

No error response MUST reveal which identifier exists or what credential was expected.

Endpoints requiring a valid Bearer JWT return `IDENTITY_022` (401) when the token is absent, invalid, or the session has been revoked. `IDENTITY_010` is reserved for future RBAC insufficient-permissions (403) responses (Phase 14).

---

## E01 Error Codes

| Code | HTTP | Meaning |
|---|---|---|
| `IDENTITY_001` | 400 | Validation failure (field-level) |
| `IDENTITY_002` | 401 | Invalid credentials (no disambiguation of which) |
| `IDENTITY_003` | 401 | OTP invalid or expired |
| `IDENTITY_004` | 423 | Account locked |
| `IDENTITY_005` | 429 | Rate limit exceeded |
| `IDENTITY_006` | 404 | Resource not found (generic; no entity disclosure) |
| `IDENTITY_007` | 409 | Conflict (e.g., mobile already registered) |
| `IDENTITY_008` | 401 | Token expired |
| `IDENTITY_009` | 401 | Token revoked |
| `IDENTITY_010` | 403 | Insufficient permissions (reserved; Phase 14 RBAC) |
| `IDENTITY_011` | 422 | Step-up authentication required |
| `IDENTITY_012` | 400 | Idempotency key reuse with differing payload |
| `IDENTITY_013` | 409 | MFA already enrolled |
| `IDENTITY_014` | 401 | Invalid or expired MFA code or token |
| `IDENTITY_015` | 401 | Refresh token reuse detected; session revoked |
| `IDENTITY_016` | 423 | PIN credential blocked; use recovery flow |
| `IDENTITY_017` | 400 | PIN complexity violation (length, sequential, repeated, common) |
| `IDENTITY_018` | 401 | Setup token or Bearer token required |
| `IDENTITY_019` | 422 | Required field missing (PIN, MFA enrollment, or MFA verification) |
| `IDENTITY_020` | 409 | PIN already set for this account |
| `IDENTITY_021` | 404 | Device not found |
| `IDENTITY_022` | 401 | Bearer token required (missing, invalid, or session expired) |
| `IDENTITY_023` | 403 | Device verification required; challenge_id included in body |
| `IDENTITY_024` | 422 | device_fingerprint field required |

## Registration

### POST /v1/auth/register

Initiate customer registration. Creates a pre-verification user record and sends an OTP.

**Idempotency**: Required. Idempotent on `X-Idempotency-Key` within the platform window.

**Request**:
```json
{
  "mobile_number": "+26771234567",
  "actor_type": "CUSTOMER"
}
```

**Response 202 Accepted**:
```json
{
  "success": true,
  "data": {
    "challenge_id": "uuid",
    "expires_at": "2026-08-21T10:05:00Z",
    "resend_at": "2026-08-21T10:01:00Z",
    "masked_destination": "+267 *** *** 567"
  }
}
```

**Error responses**: `IDENTITY_001` (validation), `IDENTITY_007` (already registered), `IDENTITY_005` (rate limit).

---

### POST /v1/auth/otp/verify

Verify OTP to complete registration or authenticate.

**Idempotency**: Required.

**Request**:
```json
{
  "challenge_id": "uuid",
  "otp": "123456"
}
```

**Response 200 OK** (registration flow — PIN not yet set):
```json
{
  "success": true,
  "data": {
    "user_id": "uuid",
    "setup_token": "opaque-short-lived-token",
    "next_step": "SET_PIN"
  }
}
```

**Response 200 OK** (login flow — fully authenticated):
```json
{
  "success": true,
  "data": {
    "access_token": "eyJ...",
    "refresh_token": "opaque-256-bit-token",
    "token_type": "Bearer",
    "expires_in": 900,
    "session_id": "uuid"
  }
}
```

**Error responses**: `IDENTITY_003` (invalid/expired OTP), `IDENTITY_001` (validation), `IDENTITY_004` (account locked after max attempts).

---

### POST /v1/auth/otp/resend

Resend OTP for an active challenge.

**Idempotency**: Required.

**Request**:
```json
{
  "challenge_id": "uuid"
}
```

**Response 200 OK**:
```json
{
  "success": true,
  "data": {
    "resend_at": "2026-08-21T10:02:00Z",
    "expires_at": "2026-08-21T10:06:00Z",
    "remaining_sends": 4
  }
}
```

**Error responses**: `IDENTITY_003` (challenge not found/expired), `IDENTITY_005` (resend cooldown or hourly limit).

## PIN Management

### POST /v1/auth/pin/set

Set PIN after successful OTP verification during registration.

**Auth**: Either `X-Setup-Token` header (unauthenticated post-registration flow) OR `Authorization: Bearer <token>` (authenticated re-set flow). Exactly one must be present.

**Idempotency**: Required.

**Headers**:
```
X-Setup-Token: <opaque-single-use-token-from-otp-verify>
```
*or*
```
Authorization: Bearer <access_token>
```

**Request**:
```json
{
  "pin": "246810"
}
```

**Response 201 Created**:
```json
{
  "success": true
}
```

The setup token is consumed on first use (single-use). Presenting the same token a second time returns `IDENTITY_018`. After PIN is set the client must perform a full login to obtain session tokens.

**Error responses**: `IDENTITY_016` (PIN blocked), `IDENTITY_017` (PIN complexity), `IDENTITY_018` (setup token or Bearer required), `IDENTITY_019` (pin field required), `IDENTITY_020` (PIN already set).

PIN value MUST NOT appear in logs, events, responses, or error messages.

### POST /v1/auth/pin/unblock

Unblock a blocked PIN credential via OTP verification. Two-mode endpoint: initiate phase sends an OTP to the registered mobile number; complete phase verifies the OTP and unblocks the credential.

**Auth**: None required. This is a recovery endpoint for users who cannot authenticate.

**Idempotency**: Required.

**Mode 1 — Initiate (send OTP)**

**Request**:
```json
{
  "mobile_number": "+26771234567"
}
```

**Response 200 OK**:
```json
{
  "success": true,
  "data": {
    "challenge_id": "uuid"
  }
}
```

Response is identical whether the mobile number is registered or not (no identifier disclosure). When the account does not exist, `challenge_id` is `null`.

---

**Mode 2 — Complete (verify OTP and unblock)**

**Request**:
```json
{
  "challenge_id": "uuid",
  "otp": "123456"
}
```

**Response 200 OK**:
```json
{
  "success": true
}
```

**Error responses**:
- `IDENTITY_002` (401) — invalid or expired challenge ID
- `IDENTITY_003` (401) — OTP invalid or expired
- `IDENTITY_019` (422) — required field missing (neither mobile_number nor challenge_id+otp provided)

PIN credential is returned to `active` status after successful unblock. Audit event `identity.credential.pin-unblocked` is recorded.

## Authentication (Login)

### POST /v1/auth/login

Authenticate with PIN (or password for Admin/Web).

**Idempotency**: Required.

**Request**:
```json
{
  "identifier": "+26771234567",
  "credential_type": "pin",
  "credential": "123456",
  "device_fingerprint": "base64-encoded-fingerprint"
}
```

`credential_type`: `pin` | `password` | `otp`

**Response 200 OK**:
```json
{
  "success": true,
  "data": {
    "access_token": "eyJ...",
    "refresh_token": "opaque-256-bit-token",
    "token_type": "Bearer",
    "expires_in": 900,
    "session_id": "uuid",
    "mfa_required": false,
    "new_device_detected": false
  }
}
```

**Response 200 OK** (MFA required):
```json
{
  "success": true,
  "data": {
    "mfa_required": true,
    "mfa_token": "opaque-mfa-token",
    "methods": ["totp", "fido2"],
    "expires_in": 300
  }
}
```
`methods`: array of enrolled MFA types available for this login (`totp`, `fido2`). `expires_in`: seconds until the `mfa_token` expires (default 300 s). Session tokens are NOT issued; call `POST /v1/auth/mfa/verify` to complete login.

**Response 403** (unrecognised device — AC-009):
```json
{
  "success": false,
  "error": {
    "code": "IDENTITY_023",
    "message": "Device verification required.",
    "challenge_id": "uuid",
    "trace_id": "uuid"
  }
}
```
Session tokens are NOT issued. The client must complete device verification via `POST /v1/auth/devices/verify` before logging in again.

**Error responses**: `IDENTITY_002` (credentials invalid), `IDENTITY_004` (account locked), `IDENTITY_005` (rate limit), `IDENTITY_023` (device verification required).

`credential` value MUST NOT appear in logs, events, or responses.

---

### POST /v1/auth/login/biometric

Authenticate with biometric assertion (challenge-response).

**Idempotency**: Required.

**Step 1 — Request challenge**:

`GET /v1/auth/login/biometric/challenge`

No request body. The server generates a cryptographic nonce and stores its hash in Redis with a 120 s TTL.

Response:
```json
{
  "success": true,
  "data": {
    "nonce": "64-char-hex-nonce",
    "expires_in": 120
  }
}
```

**Step 2 — Submit assertion**:

`POST /v1/auth/login/biometric`

```json
{
  "nonce": "64-char-hex-nonce",
  "user_id": "uuid",
  "credential_id": "uuid",
  "signed_assertion": "base64-signed-assertion",
  "device_fingerprint": "base64-encoded-fingerprint"
}
```

Response: identical to PIN login success.

Biometric data MUST NOT transit to the backend. Only cryptographic assertion/signature is sent.

### POST /v1/auth/mfa/enroll/fido2

Initiate FIDO2/WebAuthn credential enrollment. Returns a server-generated challenge that the authenticator device must sign.

**Auth**: Bearer token required (`identity.auth` middleware).

**Idempotency**: Not required (read-only challenge generation).

**Request**: Empty body or `{}`.

**Response 200 OK**:
```json
{
  "success": true,
  "data": {
    "enrollment_id": "uuid",
    "challenge": "base64url-encoded-challenge"
  }
}
```

**Error responses**: `IDENTITY_022` (Bearer token missing or invalid), `IDENTITY_013` (FIDO2 not enabled for actor type — Admin FIDO2 config disabled).

---

### POST /v1/auth/mfa/enroll/fido2/confirm

Confirm FIDO2 enrollment by submitting the signed credential. Phase 12: stores `credential_id`, `public_key`, and initial `sign_count`; full attestation verification deferred to Phase 21.

**Auth**: Bearer token required (`identity.auth` middleware).

**Idempotency**: Recommended.

**Request**:
```json
{
  "enrollment_id": "uuid",
  "credential_id": "base64url-credential-id",
  "public_key": "base64url-or-pem-public-key",
  "sign_count": 0
}
```

`sign_count`: initial counter value from the authenticator (integer ≥ 0).

**Response 200 OK**:
```json
{
  "success": true
}
```

**Error responses**: `IDENTITY_019` (enrollment_id, credential_id, or public_key missing), `IDENTITY_014` (invalid enrollment_id or expired challenge), `IDENTITY_022` (Bearer token missing or invalid).

---

### POST /v1/auth/mfa/disable

Revoke an enrolled MFA credential for the authenticated user. After disabling, subsequent logins bypass the MFA gate for the removed method.

**Auth**: Bearer token required (`identity.auth` middleware).

**Idempotency**: Recommended.

**Request**:
```json
{
  "method": "totp"
}
```

`method`: `totp` | `fido2`.

**Response 200 OK**:
```json
{
  "success": true
}
```

**Error responses**: `IDENTITY_022` (Bearer token missing or invalid), `IDENTITY_006` (no matching MFA credential found).

Disabling MFA is an audited action (`identity.mfa.disabled` event). Re-enrollment requires completing the full enroll → confirm flow again.

## Step-Up Authentication

### POST /v1/auth/step-up/initiate

Initiate step-up for a high-value operation.

**Auth**: Bearer token required.

**Request**:
```json
{
  "scope": "payment:high-value",
  "operation_context": {
    "amount": 15000,
    "currency": "BWP"
  }
}
```

**Response 200 OK — step-up required** (amount exceeds threshold or risk signal present):
```json
{
  "success": true,
  "data": {
    "step_up_required": true,
    "step_up_token": "opaque-step-up-challenge-token",
    "methods": ["totp", "pin", "biometric"],
    "expires_at": "2026-08-21T10:05:00Z"
  }
}
```

**Response 200 OK — step-up not required** (amount below threshold, no risk signal):
```json
{
  "success": true,
  "data": {
    "step_up_required": false
  }
}
```

`step_up_required` is always present and is the discriminator. When `false`, `step_up_token`, `methods`, and `expires_at` are absent.

---

### POST /v1/auth/step-up/verify

Complete step-up authentication.

**Auth**: Bearer token required.

**Request**:
```json
{
  "step_up_token": "opaque-step-up-challenge-token",
  "method": "totp",
  "credential": "123456"
}
```

**Response 200 OK**:
```json
{
  "success": true,
  "data": {
    "step_up_access_token": "eyJ...",
    "scope": "payment:high-value",
    "expires_in": 300
  }
}
```

The step-up access token is purpose-scoped and audience-restricted. It MUST be used for the target operation only.

## Admin Session Management

### POST /v1/admin/sessions/{session_id}/revoke

Immediately revoke any user's session. Admin-only endpoint; the caller must be authenticated with an ADMIN actor type.

**Auth**: Bearer token required. Actor type must be `ADMIN` (enforced inline until E04 RBAC ships).

**Idempotency**: Required.

**Path parameter**: `session_id` — UUID of the session to revoke.

**Request**: Empty body.

**Response 200 OK**:
```json
{
  "success": true
}
```

**Error responses**:
- `IDENTITY_022` (401) — Bearer token absent, invalid, or session revoked
- `IDENTITY_013` (403) — Caller is not an ADMIN actor (pre-E04 placeholder; will become `IDENTITY_010` when E04 RBAC middleware ships)
- `IDENTITY_011` (404) — Session not found or already revoked

**Authorization**: The route is protected by `identity.auth` middleware. An inline actor-type check rejects non-ADMIN callers with 403 until E04 authorization middleware is active.

**Audit**: On success, emits `identity.session.revoked` to `platform.audit_events` with `actor_id` = admin user ID, `resource_id` = session ID, `outcome` = success, `ip_hash` = HMAC-SHA256 of admin request IP (BR-021; AC-019).

## Device Management

### POST /v1/auth/devices/verify

Verify a new device via OTP and issue a full session. Completes the device verification flow
initiated when `POST /v1/auth/login` returns 403 IDENTITY_023 for an unrecognized device.

**Auth**: None required. This is a pre-session endpoint — the caller does not yet hold a session.

**Idempotency**: Not required (OTP challenges are single-use; replay is rejected by challenge state).

**Flow**: When login from an unrecognized device triggers IDENTITY_023, the error response includes a
`challenge_id` and delivers an OTP to the user's registered mobile number. The client submits both to
this endpoint; on success, the device is trusted and a full session is issued.

**Request**:
```json
{
  "challenge_id": "uuid",
  "otp": "123456"
}
```

**Response 200 OK**:
```json
{
  "success": true,
  "data": {
    "access_token": "eyJ...",
    "refresh_token": "eyJ...",
    "token_type": "Bearer",
    "expires_in": 3600,
    "session_id": "uuid"
  }
}
```

**Error responses**:
- IDENTITY_003 (401) — OTP invalid or expired
- IDENTITY_002 (401) — Challenge ID invalid or expired
- IDENTITY_019 (422) — `challenge_id` or `otp` absent from request body

**Post-verification effects**:
- Device status promoted to `trusted` in `identity.devices`; `trusted_at` timestamp set.
- Full session issued (access token + refresh token).
- OTP challenge consumed — cannot be reused.
- Audit event `identity.device.registered` recorded in `platform.audit_events` with `actor_id` = user ID, `resource_id` = device ID, `outcome` = success, `ip_hash` = HMAC-SHA256 of request IP (BR-021).

## JWT Access Token Structure

```json
{
  "iss": "https://identity.olekard.com",
  "sub": "user-uuid",
  "aud": ["api.olekard.com"],
  "iat": 1724234400,
  "exp": 1724235300,
  "nbf": 1724234400,
  "jti": "unique-token-id",
  "session_id": "session-uuid",
  "actor_type": "USER",
  "roles": ["CUSTOMER"],
  "device_id": "device-uuid-or-null",
  "kid": "key-id-for-jwks-lookup"
}
```

**Step-up token additional claims**:
```json
{
  "step_up_scope": "payment:high-value",
  "step_up_verified_at": 1724234400
}
```

**Service identity token additional claims**:

## JWT Configuration Policy (DB-001 Resolution)

JWT configuration is split across two layers:

| Parameter | Storage | Key / Env |
|---|---|---|
| Access token TTL (per actor) | `platform.configuration_values` | `auth.session.inactivity_ttl_admin`, `auth.session.inactivity_ttl_customer`, `auth.session.inactivity_ttl_agent` |
| Refresh token TTL | `platform.configuration_values` | `auth.refresh_token.ttl` |
| `iss` (issuer) | Environment | `APP_URL` |
| `aud` (audience) | Environment | `APP_URL` |
| Signing private key | Secret manager / Environment | `IDENTITY_JWT_PRIVATE_KEY` |
| Old public key (rotation) | Secret manager / Environment | `IDENTITY_JWT_OLD_PUBLIC_KEY` |

`auth.jwt.access_token_ttl` is NOT a separate config key — access token TTL is the same as the actor-type session inactivity TTL. `auth.jwt.issuer` and `auth.jwt.audience` are intentionally environment-only and are NOT stored in `platform.configuration_values`.
