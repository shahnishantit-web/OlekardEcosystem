## Financial Safety Requirements

- [ ] CHK008 - Is the one-time-write rule for `provider_reference` expressed as a precise, testable obligation — specifically that NULL → value is the only permitted mutation and any subsequent write throws an exception — rather than as a general immutability statement? [Clarity, Spec §FR-E1000-010, Data Model §platform.provider_external_references]

- [ ] CHK009 - Is the speculative record requirement (FR-E1000-026) explicit about WHEN the record must be created (before the provider call is initiated), not just that it should exist? [Clarity, Spec §FR-E1000-026]

- [ ] CHK010 - Is the `reference_confirmed_at` field purpose — specifically that it is set atomically with the first write to `provider_reference` — stated as a constraint, not merely a description? [Clarity, Data Model §platform.provider_external_references]

- [ ] CHK011 - Are the requirements for handling a missing `providerReference` in a `ProviderResponse` (surrogate generation, audit warning, no blocking of the platform operation) all documented explicitly in FR-E1000-011? [Completeness, Spec §FR-E1000-011]

- [ ] CHK012 - Does the spec specify what happens when a `ProviderException` is thrown during a financial operation — specifically that the calling financial service MUST handle compensating events or rollback, and that the contract layer only defines the seam? [Clarity, Spec §FR-E1000-024]

- [ ] CHK013 - Is the non-null, non-zero amount invariant for financial `ProviderRequest` stated as a constructor-time obligation (not a runtime validation option)? [Clarity, Spec §FR-E1000-025, Data Model §ProviderRequest]

- [ ] CHK014 - Are the EXCEPTION state transition rules (reason required, owner required, timestamp required, no silent resolution) stated as validation errors that MUST be enforced at the service layer, not as advisory guidelines? [Completeness, Spec §US5/AC2–AC4, Contracts §7]

## Security and Credential Boundary Requirements

- [ ] CHK015 - Is the credential boundary requirement (no credential in any contract, value object, request, response, audit event, log, or metric label) stated as an exhaustive list rather than "credentials must not be in domain code" (which leaves ambiguity about outbox payloads and metric labels)? [Clarity, Spec §FR-E1000-015]

- [ ] CHK016 - Is the distinction between "provider identifier key" (a config key string, allowed in audit/metrics) and "provider credential" (never allowed anywhere) explicitly defined and consistently applied across all requirements? [Consistency, Spec §FR-E1000-013, §FR-E1000-020, §FR-E1000-021]

- [ ] CHK017 - Are the metric label restrictions (no user ID, mobile number, raw IP, account number, token ID, session ID, credential, or secret name) specified as a closed list, rather than an open-ended "no PII"? [Clarity, Spec §FR-E1000-021]

- [ ] CHK018 - Is the `metadata` field on `ProviderRequest` restricted by a blocklist of credential-bearing key names (api_key, secret, password, token, etc.) explicitly stated as a constructor-time validation? [Completeness, Data Model §ProviderRequest]

- [ ] CHK019 - Does the spec state that `NullProviderAdapter` MUST NOT be registered as a live container binding in production — or is this only a note in research.md without a formal requirement? [Gap, Contracts §NullProviderAdapter, Research §R-007]

## Observability Requirements

- [ ] CHK020 - Are all required fields for the audit event emitted by `send()` listed exhaustively in FR-E1000-020 (operation type, platform entity ID, provider key, normalized outcome, raw status code, provider reference, correlation ID, IP hash, duration)? [Completeness, Spec §FR-E1000-020]

- [ ] CHK021 - Is the requirement that audit events MUST be emitted for EVERY call — success and failure alike — stated explicitly, or does the spec only cover the success path? [Coverage, Spec §FR-E1000-020]

- [ ] CHK022 - Are the three metric types (call counter, latency histogram, and the entity they are labeled by) each precisely specified — or is "emit metrics" left underspecified? [Clarity, Spec §FR-E1000-021]
