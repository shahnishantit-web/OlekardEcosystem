# Implementation Plan: P07 — Durable Idempotency, Concurrency and Recovery

**Branch**: `056-durable-idempotency-recovery` | **Date**: 2026-10-21 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/056-durable-idempotency-recovery/spec.md`

---

## Summary

P07 hardens the payment system's financial safety against four failure modes: network retry double-charges (Redis+DB idempotency cache), server crash between persist-before-execute and adapter call (crash recovery job), database deadlocks under concurrency (bounded retry with consistent lock order), and genuine provider double-captures (Guard D evidence recording). All changes are additive to the existing `PaymentOrchestrationService`, `PaymentAttemptTimeoutJob`, and controller stack from P01–P06.

## Phase 0: Research Findings Summary

All NEEDS CLARIFICATION items are resolved in `research.md`. Key decisions:

1. **Hybrid Option C** — PostgreSQL authoritative + Redis 24h TTL cache. Fall-through on Redis miss.
2. **Request hash** — SHA-256 of ksort-normalised JSON body. Stored in DB; checked on replay.
3. **Table**: `payment.payment_idempotency_records` — 90-day retention, unique on `(actor_id, scope, idempotency_key)`.
4. **Crash recovery** — Periodic scan job for SUBMITTING attempts older than threshold. Per-attempt recovery uses `queryPaymentStatus(operation_id)` as fallback when `provider_reference_id` is null.
5. **Deadlock retry** — `DeadlockRetryTrait` catching SQLSTATE `40P01`; up to 3 retries with exponential backoff; `ConcurrentModificationException` on exhaustion → HTTP 409.
6. **Guard D** — `DuplicateCapture` in `handleOutcome()`: same-succeeded, different-ref, non-null. Creates `ReconciliationException(DuplicateCapture)`, returns silently.
7. **Controller-layer idempotency** — Not middleware; injected into three state-changing controllers.

## Implementation Rules (Non-Negotiable)

- **Idempotency service is injected, never instantiated directly** — allows mock in tests
- **Crash recovery never calls `initiatePayment()` on a SUBMITTING attempt** — only `queryPaymentStatus()`
- **Guard D must come after Guard A** — Guard A handles true idempotent replay; Guard D handles the distinct different-ref case
- **Deadlock retry wraps `DB::connection('platform')->transaction()` only** — never wraps `DB::connection('payment')->transaction()` (different connection, different lock domain)
- **`payment_idempotency_records` is NOT a replace for `payment_intents.idempotency_key`** — existing domain-level dedup remains; HTTP-layer cache is additive
- **PHPStan `@phpstan-param` annotations** required on any `array` parameters in new services
