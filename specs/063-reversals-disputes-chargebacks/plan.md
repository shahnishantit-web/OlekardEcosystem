# Implementation Plan: P16 — Reversals, Disputes and Chargebacks

**Branch**: `063-reversals-disputes-chargebacks` | **Date**: 2026-10-24 | **Spec**: [spec.md](spec.md)

## Summary

Implement a `PaymentDisputeCase` entity and lifecycle engine within the existing Payment module to handle provider-originated reversals, disputes, and chargebacks per LC12. Covers: authenticated ingestion and deduplication; operator-authorised financial holds; domain entitlement coordination; idempotent correcting ledger journals; double-compensation guard against prior refunds; admin management APIs; customer read-only summary; outbox events; and an operator runbook.

## Technical Context

**Language/Version**: PHP 8.4+ (Laravel 12)

**Primary Dependencies**: Existing Payment module services (`ReconciliationExceptionService`, `OutboxEventPublisher`, `LedgerModuleContract`); `BankCallbackVerifier`; `InboxDispatcher` (E25/P10); `PaymentRefundRepositoryInterface::sumConfirmedRefundsForAttempt()`

**Storage**: PostgreSQL — `payment` schema. Three new tables: `payment_dispute_cases`, `dispute_case_events`, `dispute_holds`.

**Testing**: PHPUnit (unit tests no Docker; feature tests `@group docker`); PHPStan level 8.

**Target Platform**: Laravel Horizon background jobs on the `payment` queue.

**Project Type**: Domain service layer + REST API extension within Payment module.

**Performance Goals**: Admin list API consistent with existing Payment module SLAs. No new background polling jobs (dispute events are push-based via E25 inbox).

**Constraints**: No wallet balance mutation. No direct ledger entry modification. All correcting journals via `LedgerModuleContract::postEntry()` outside DB transactions with idempotency keys. All state changes audited in `dispute_case_events` append-only table. Hold mechanism does NOT debit consumer wallet.

**Scale/Scope**: Extends the 37-file Payment module with ~25 new files. No new service providers needed; binds into `PaymentServiceProvider`.
