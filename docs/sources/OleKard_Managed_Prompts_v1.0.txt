OleKard Payment Implementation Prompt Pack
Separate work packages for Claude Code and Spec Kit
Version 1.0  |  20 October 2026  |  Architecture baseline version 1.1
Purpose and execution approach
This pack converts the Shared Payment Architecture into 34 separately manageable prompts. Each prompt is a bounded feature specification or review package with a role owner, prerequisites, source references, tasks, verification and a completion report. It supports the existing Laravel, PostgreSQL, Redis, Next.js and Flutter implementation without requiring a new payment engine per business module.
Use one selected prompt at a time. P00 assesses the repository, P01 establishes contracts and the remaining packages implement or verify defined scope. Create stories and tasks inside each work package using the repository’s existing numbering. P IDs are management references, not replacements for approved epic IDs.
Source: OleKard_Shared_Payment_Architecture.docx, document version 1.1 dated 19 October 2026, including 16 lifecycle flows. This is a companion prompt pack; the architecture document remains the governing requirement baseline. Bank names remain placeholders until actual providers and documentation are supplied.
How to run a prompt
Place the architecture document in an accessible repository documentation folder and give Claude Code its actual path. Retain the Word file or extract its complete content to a checked-in text format according to project conventions.
Run P00 first and P01 next. Use the dependency register below to choose subsequent ready packages. Dependencies mean verified required contracts or evidence, not merely that another session was opened.
Copy the complete selected prompt from its START PROMPT to END PROMPT markers. Its safety, workflow and reporting instructions are included so it can be used in a fresh session.
For each implementation package, use installed Spec Kit stages to specify, clarify blocking decisions, plan, create tasks, analyse consistency and implement. Do not assume command names, a custom converge command or a particular Spec Kit version.
After completion, review evidence and update the register before selecting another prompt. A BLOCKED/PARTIAL package does not imply all downstream work must stop; proceed only where the actual prerequisite is satisfied.
For an existing implemented feature, assess and complete gaps rather than rebuild. Treat external-provider certification, real operating permission and production release as separate acceptance gates.
Managerial control model
Use a lifecycle of NOT STARTED → READY → IN PROGRESS → REVIEW → COMPLETED, with PARTIAL, BLOCKED and DEFERRED recorded explicitly. COMPLETED means the selected deliverables and checks passed; it does not mean the whole platform is production-ready. Record specification status, implementation status, certification status and release status separately.
At every handover retain: work-package ID, repository epic/story/task links, branch/commit, source version, implemented scope, test evidence, unresolved decisions, blockers, next permitted action and restart notes. Assign real people and dates in your project tracker; role names below are suggested responsibilities only. Do not invent completion dates, effort estimates or test results.
